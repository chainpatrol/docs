## Overview

Upload a file to ChainPatrol and get back a URL. Pass that URL to
[Create Report](/external-api/report-create) in `attachmentUrls` to attach the file as
evidence.

This is a two-step flow, and the two steps are separate requests:

1. `POST /attachment/upload` — send the bytes, receive a URL.
2. `POST /report/create` — include that URL in `attachmentUrls`.

See [Creating Reports](/external-api/creating-reports) for the complete flow with worked
examples.

<Info>
  **You do not have to use this endpoint.** `attachmentUrls` accepts any publicly
  reachable URL, so if you already host your evidence somewhere we can fetch, keep passing
  those links. This endpoint exists so you do not *have* to host them.
</Info>

<Note>
  **It is not images only.** Screenshots are the most common attachment, but `.eml` and
  `.msg` message files, PDFs, Word documents, CSVs, and plain text are all supported — see
  [Supported file types](#supported-file-types). Images are displayed inline on the report
  in the dashboard; everything else is listed as a downloadable file that our takedown team
  can forward to a registrar or host.
</Note>

```
POST https://app.chainpatrol.io/api/v2/attachment/upload
```

## Authentication

Include your API key in the `X-API-KEY` header, the same as every other endpoint — see
[Authentication](/external-api/authentication):

```bash
X-API-KEY: your_api_key_here
```

Read-only API keys cannot upload — that role exists for cross-organization reads. Uploads
are recorded against the organization behind the key, and count towards its API usage.

## Two ways to send a file

The endpoint accepts either shape. Pick whichever your HTTP client makes easier.

### Raw body

Send the file bytes as the request body and the file name as the `fileName` query
parameter. One file per request.

<CodeGroup>

```bash cURL
curl -X POST 'https://app.chainpatrol.io/api/v2/attachment/upload?fileName=evidence.eml' \
  -H 'X-API-KEY: YOUR_API_KEY_HERE' \
  --data-binary '@evidence.eml'
```

```typescript TypeScript
import { readFile } from "node:fs/promises";

const bytes = await readFile("evidence.eml");

const response = await fetch(
  "https://app.chainpatrol.io/api/v2/attachment/upload?fileName=evidence.eml",
  {
    method: "POST",
    headers: { "X-API-KEY": "YOUR_API_KEY_HERE" },
    body: bytes,
  }
);

const { attachments } = await response.json();
console.log(attachments[0].url);
```

```python Python
import requests

with open("evidence.eml", "rb") as file:
    response = requests.post(
        "https://app.chainpatrol.io/api/v2/attachment/upload",
        params={"fileName": "evidence.eml"},
        headers={"X-API-KEY": "YOUR_API_KEY_HERE"},
        data=file,
    )

attachments = response.json()["attachments"]
print(attachments[0]["url"])
```

</CodeGroup>

<Warning>
  `fileName` is required for raw uploads, and must appear exactly once. Repeating it
  (`?fileName=a.eml&fileName=b.eml`) is rejected with a `400`.
</Warning>

### Multipart form

Send `multipart/form-data` with one or more file parts. This is what a browser form,
Postman's file picker, or `curl -F` produces. Up to **10 files** per request.

The file name comes from each part's own filename, so the `fileName` query parameter is
ignored here. Non-file form fields are ignored, and the part names themselves do not
matter — send them all as `file` if you like.

<CodeGroup>

```bash cURL
curl -X POST 'https://app.chainpatrol.io/api/v2/attachment/upload' \
  -H 'X-API-KEY: YOUR_API_KEY_HERE' \
  -F 'file=@evidence.eml' \
  -F 'file=@screenshot.png'
```

```typescript TypeScript
const form = new FormData();
form.append("file", new File([emlBytes], "evidence.eml"));
form.append("file", new File([pngBytes], "screenshot.png"));

const response = await fetch(
  "https://app.chainpatrol.io/api/v2/attachment/upload",
  {
    method: "POST",
    headers: { "X-API-KEY": "YOUR_API_KEY_HERE" },
    body: form,
  }
);

const { attachments } = await response.json();
console.log(attachments.map((attachment) => attachment.url));
```

```python Python
import requests

with open("evidence.eml", "rb") as eml, open("screenshot.png", "rb") as png:
    response = requests.post(
        "https://app.chainpatrol.io/api/v2/attachment/upload",
        headers={"X-API-KEY": "YOUR_API_KEY_HERE"},
        files=[
            ("file", ("evidence.eml", eml)),
            ("file", ("screenshot.png", png)),
        ],
    )

attachments = response.json()["attachments"]
print([attachment["url"] for attachment in attachments])
```

</CodeGroup>

## Request

| Parameter        | In           | Required          | Description                                                                                       |
| ---------------- | ------------ | ----------------- | ------------------------------------------------------------------------------------------------- |
| `X-API-KEY`      | header       | Yes               | Your API key.                                                                                     |
| `fileName`       | query        | Raw uploads only  | File name for the uploaded bytes, including the extension (for example `evidence.eml`).           |
| body             | body         | Yes               | The file bytes, or a `multipart/form-data` body with one or more file parts.                       |

### File name handling

- The extension decides how we store and serve the file, so it has to be present and on
  the [supported list](#supported-file-types). Matching is case-insensitive.
- Directory components are stripped: `../../secrets/evidence.eml` is stored as
  `evidence.eml`.
- Names must be 200 characters or fewer and contain no control characters.
- Your name is otherwise preserved as-is. That matters because it is the name shown on the
  report, and the name a registrar or hosting provider sees when our takedown team forwards
  the file — so `phishing-email.eml` is worth more than `attachment1.eml`.
- Uploading two files with the same name is fine. Each upload is stored on its own path, so
  nothing is ever overwritten and the name you sent is what comes back.

## Supported file types

The content type we serve the file with is derived from the extension, not from the
`Content-Type` header you send, so any header your client sets is ignored.

| Extension        | Stored as                                                                 |
| ---------------- | ------------------------------------------------------------------------- |
| `.eml`           | `message/rfc822`                                                          |
| `.msg`           | `application/vnd.ms-outlook`                                              |
| `.pdf`           | `application/pdf`                                                         |
| `.doc`           | `application/msword`                                                      |
| `.docx`          | `application/vnd.openxmlformats-officedocument.wordprocessingml.document` |
| `.csv`           | `text/csv`                                                                |
| `.txt`           | `text/plain`                                                              |
| `.png`           | `image/png`                                                               |
| `.jpg`, `.jpeg`  | `image/jpeg`                                                              |
| `.gif`           | `image/gif`                                                               |
| `.webp`          | `image/webp`                                                              |
| `.avif`          | `image/avif`                                                              |
| `.bmp`           | `image/bmp`                                                               |

Anything else is rejected with a `400`. `.svg` and `.html` are deliberately excluded:
they render as active content, and files we serve should not.

If you need a format that is not on this list, email
[support@chainpatrol.io](mailto:support@chainpatrol.io) — a common workaround is to send
the file inside a supported container (a PDF export, or the raw `.eml`).

## Limits

| Limit                | Value                       | What happens when you exceed it            |
| -------------------- | --------------------------- | ------------------------------------------ |
| Request body size    | 4 MB (4,194,304 bytes)      | `413`                                      |
| Files per request    | 10 (multipart)              | `400`                                      |
| File name length     | 200 characters              | `400`                                      |
| Requests per minute  | 60 per organization         | `429`                                      |

The size limit applies to the whole request body, so in a multipart request all parts share
the same 4 MB budget. For anything larger, split it across requests and attach the
resulting URLs to the same report.

The rate limit is counted per organization, or per API key for keys that are not tied to
one.

## Response

`200 OK` returns one entry per uploaded file, in the order they were sent.

```json
{
  "attachments": [
    {
      "url": "https://upcdn.io/ACCOUNT/raw/uploads/2026/09/03/api-attachments/org-42/8f14e45f-ea3a-4f0b-9b1a-1c2d3e4f5a6b/evidence.eml",
      "fileName": "evidence.eml",
      "sizeBytes": 48210
    },
    {
      "url": "https://upcdn.io/ACCOUNT/raw/uploads/2026/09/03/api-attachments/org-42/2c1f3b7e-55d9-4a7e-8a0e-7b6c5d4e3f21/screenshot.png",
      "fileName": "screenshot.png",
      "sizeBytes": 182934
    }
  ]
}
```

| Field                     | Type   | Description                                                                    |
| ------------------------- | ------ | ------------------------------------------------------------------------------ |
| `attachments`             | array  | One entry per uploaded file, in request order.                                  |
| `attachments[].url`       | string | The URL to pass to `report.create` in `attachmentUrls`.                         |
| `attachments[].fileName`  | string | The stored file name, after sanitising.                                         |
| `attachments[].sizeBytes` | number | Size of the stored file in bytes.                                               |

<Warning>
  Treat `url` as opaque. Store it and pass it through — do not parse it, and do not try to
  construct one yourself. The path layout is an implementation detail and can change.

  The URL is served from our CDN and is reachable by anyone who has it, which is what lets
  us forward evidence to registrars and hosting providers. The path is not guessable, but
  do not upload anything you would not want a third party to see if the link were shared.
</Warning>

## Error responses

Every error returns a JSON body with a single `error` string.

| Status | Meaning                                                                                              |
| ------ | ---------------------------------------------------------------------------------------------------- |
| `400`  | Bad request — unsupported extension, missing or repeated `fileName`, empty body, an empty file part, malformed multipart, no file parts, or more than 10 files. |
| `401`  | Missing, invalid, or expired API key.                                                                 |
| `403`  | Read-only API key. Read-only keys exist for cross-organization reads and cannot upload.               |
| `405`  | Wrong method — this endpoint is `POST` only.                                                          |
| `413`  | Request body larger than 4 MB.                                                                        |
| `429`  | Rate limit exceeded (60 requests per minute per organization).                                        |
| `502`  | We could not store the file. Safe to retry.                                                           |

Examples:

```json Unsupported extension
{
  "error": "fileName must end in one of: .avif, .bmp, .csv, .doc, .docx, .eml, .gif, .jpeg, .jpg, .msg, .pdf, .png, .txt, .webp"
}
```

```json Missing fileName on a raw upload
{
  "error": "A fileName query parameter is required for raw uploads, for example ?fileName=evidence.eml"
}
```

```json Over the size limit
{
  "error": "Upload exceeds the 4194304 byte request limit."
}
```

```json Rate limited
{
  "error": "Rate limit exceeded. Please try again later."
}
```

## Best practices

- **Upload first, report second.** Nothing links the file to a report until you pass the
  URL to `report.create`. An uploaded file that is never referenced simply sits unused.
- **Attach every file to a report.** Uploads are not visible in the dashboard on their
  own; the report is what makes them reviewable.
- **Use meaningful file names.** The name follows the file into the dashboard and into
  outbound takedown emails.
- **Retry `502` and `429`, not `400`.** A `4xx` other than `429` means the request itself
  needs fixing; retrying it unchanged will fail the same way.
- **Send `.eml` rather than a screenshot of an email** when you have it. The raw message
  carries headers, which is what registrars and email providers act on.

## Notes

- This endpoint is not part of the generated OpenAPI specification, because it takes raw
  bytes and multipart bodies rather than JSON. Everything it accepts is documented on this
  page.
- There is no endpoint for listing, replacing, or deleting an upload. To correct a
  mistake, upload the right file and reference that URL instead; to remove evidence from a
  report, contact [support@chainpatrol.io](mailto:support@chainpatrol.io).
- Files are not scanned for malware. Do not treat an uploaded file as safe to open just
  because it came through the API.
