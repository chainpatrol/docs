## Overview

List every asset reported for your organization, by your team or by ChainPatrol, with
where each one stands: still under investigation, escalated to you, blocked or
allowed, and how far its takedown has got.

Use it to keep a threat-intel platform, SIEM or ticketing system in step with
ChainPatrol. Page through it once for a backfill, then poll with `updatedSince` and
upsert each row on `id`.

To list only confirmed threats blocked in a date range, use
[`/threats/list`](/external-api/threats-list). To list unconfirmed detections, use
[`/detection/list`](/external-api/detection-list).

## Quick Start

### Authentication

Include your API key in the `X-API-KEY` header. Organization API keys resolve the
organization from the key, so `slug` is optional for them.

```bash
X-API-KEY: <api-key>
```

### Example Request

```bash
curl --request GET \
  --url 'https://app.chainpatrol.io/api/v2/organization/threats?updatedSince=2026-11-01T00:00:00Z&per_page=500' \
  --header 'X-API-KEY: <api-key>'
```

## Query Parameters

| Parameter      | Type        | Required | Default | Description                                                                                                       |
| -------------- | ----------- | -------- | ------- | ----------------------------------------------------------------------------------------------------------------- |
| `slug`         | `string`    | ❌ No    | -       | Organization slug. Needed only when your credentials can reach more than one organization.                        |
| `updatedSince` | `string`    | ❌ No    | -       | ISO 8601 timestamp. Only threats whose asset, reports or takedown changed at or after this time. Omit to backfill. |
| `assetType`    | `AssetType` | ❌ No    | -       | Only threats of this asset type.                                                                                  |
| `per_page`     | `number`    | ❌ No    | `100`   | Threats per page, 1 to 1000.                                                                                      |
| `next_page`    | `string`    | ❌ No    | -       | The `next_page` value from the previous response.                                                                 |

## Lifecycle states

`state` sums up each asset's reports and the decision on it:

| `state`         | Meaning                                                            |
| --------------- | ------------------------------------------------------------------ |
| `investigating` | A report is open and ChainPatrol is reviewing it.                  |
| `escalated`     | A report is open and waiting on a decision from your organization. |
| `blocked`       | The asset is on the blocklist.                                     |
| `allowed`       | The asset is on the allowlist.                                     |
| `closed`        | Every report was reviewed and nothing was blocked.                 |

A decision on the asset wins over open reports: once it is blocked or allowed,
`state` stays there even if someone reports it again. An asset that was escalated,
decided and then reported again goes back to `investigating`.

The timestamps on each threat:

- `firstReportedAt`: the first report for your organization.
- `escalatedAt`: the first time the asset was escalated to your organization, or
  `null` if it never was.
- `blockedAt`: when the asset was blocked, or `null`.
- `takedown`: `null` until a takedown is opened. `submittedAt` is the first time it
  was filed with a provider, and `completedAt` the first time it was completed. If
  the site comes back, the takedown reopens: `status` goes back to `IN_PROGRESS` while
  `completedAt` keeps the first completion. Watch `status` to catch re-emergence.
- `updatedAt`: the latest change to the asset, its reports or its takedown. This is
  the value `updatedSince` compares against.

## Polling for changes

1. **Backfill.** Call without `updatedSince` and follow `next_page` until it is
   `null`. Note the time you started.
2. **Poll.** Send `updatedSince` set a few minutes before the start of your last
   successful sync, and follow `next_page` until it is `null`, keeping the same
   `updatedSince` on every page. Upsert each threat on `id`.
3. **Advance.** Use the start time of this sync as the watermark for the next one.

<Warning>
  Overlap your windows by a few minutes. A change written while a request is running
  can otherwise fall between two polls. The overlap re-sends a few threats you
  already have, which an upsert absorbs.
</Warning>

Pages are ordered by asset `id`, ascending, and the cursor is the last `id` returned,
so assets reported mid-sync land on later pages instead of shifting earlier ones. A
page can hold fewer than `per_page` threats while `next_page` is still set; keep
going until `next_page` is `null`.

```javascript
async function syncThreats(apiKey, updatedSince) {
  const threats = [];
  let nextPage = null;

  do {
    const params = new URLSearchParams({ per_page: "1000" });
    if (updatedSince) params.set("updatedSince", updatedSince);
    if (nextPage) params.set("next_page", nextPage);

    const response = await fetch(
      `https://app.chainpatrol.io/api/v2/organization/threats?${params}`,
      { headers: { "X-API-KEY": apiKey } },
    );
    if (!response.ok) throw new Error(`HTTP ${response.status}`);

    const page = await response.json();
    threats.push(...page.threats);
    nextPage = page.next_page;
  } while (nextPage);

  return threats;
}
```
